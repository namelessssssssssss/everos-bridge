# EverOS 检索方法小样本对比（2026-10-09）

结论：当前证据不支持默认开启 LLM rerank 或把每轮召回改成 agentic。`top_k` 的本地 20 条上限没有记录依据，改为官方的 `-1` 或 `1–100`；默认仍为 5。

## 官方能力与当前选择

- `enable_llm_rerank` 只在 `agent_id` + `hybrid` 生效，增加 LLM 重排步骤；用户事件查询忽略它。因此开关不能改善全部记忆轨道。
- `agentic` 用更复杂的检索过程处理问题，不能与 hybrid 的得分直接比较；官方建议 hybrid 作为起点，复杂问题效果不足时再升级，并为 agentic 配更长超时及 hybrid 回退。
- `min_score` 只对用户 episode 的 hybrid 路径生效；切换方法不能假设现有 0.3 门槛仍有效。
- 桥接层原先把 `method` 写死为 hybrid，未开放参数，仓库没有基于本空间 A/B 证明 hybrid 总是更优的记录。当前 18 秒召回预算和 20 秒 hook 上限也不足以保证 agentic 完成。

来源：[Cloud 完整文档](https://docs.evermind.ai/llms-full.txt)、[官方 API 参考](https://github.com/EverMind-AI/EverOS/blob/main/docs/api.md#post-apiv2memorysearch)。Cloud 文档以本次成功的 HTTP 读取为准；其中的延迟/成本描述属于官方建议，不作为本机实测值。

## 试验口径

只调用现有空间的 `/api/v2/memory/search`，不写探针数据。固定 `top_k=5`；用户查询传 `min_score=0.3`、`include_profile=false`；Agent 查询仅在 rerank 组额外传 `enable_llm_rerank=true`。单请求超时 55 秒，最多 3 个并发。计时从请求发出至响应完成，不包含线程排队。未经过桥接层的去重、0.55 门槛或字数截断，以便观察原始差异。

| 编号 | 轨道 | 完整问题 |
| --- | --- | --- |
| u1 | user | 之前 EverOS 写入后没有生成记忆，最终根因和修复办法是什么？ |
| u2 | user | 我在番茄UG知识仓和长期记忆机器人上的第四季度重点和组内落地边界是什么？ |
| a1 | agent | 在新设备为 Claude Code、Codex、Kimi 接入同一套 EverOS 记忆，如何验证完整性并避开配置坑？ |
| a2 | agent | 排查 EverOS 写入后 no_extraction、检索不到新记录，如何区分写入失败、抽取时序和索引延迟？ |

## 结果

10 次请求全部成功。

| 问题 | hybrid 耗时 | hybrid + LLM rerank 耗时 | agentic 耗时 |
| --- | ---: | ---: | ---: |
| u1 | 0.858 s | 不适用 | 15.132 s |
| u2 | 0.972 s | 不适用 | 20.199 s |
| a1 | 1.323 s | 6.289 s | 14.203 s |
| a2 | 1.035 s | 5.130 s | 8.127 s |

- **rerank**：a1、a2 的前 5 条 case ID 及顺序均未改变，耗时均值从 1.179 s 增至 5.710 s。得分有变化；a1 第 5 条由 0.5494 升至 0.5512，反而会越过本地 0.55 门槛，该条是 bytedcli 工具经验。两次 rerank 响应的 `agent_skills` 都为空，而基础 hybrid 返回了 skills；这些基础 skills 的得分本就低于本地门槛。不能把分数升高或输出数量变化当成准确率提高。
- **agentic 有收益的样本**：u1 的 flush 根因记录 `6ac77a80d439dd01518321e0` 从第 3 位升到第 1 位；旧时间戳问题从第 5 位升到第 2 位。
- **agentic 收益有限的样本**：u2 两种方法均在前 2 位找到目标事实，agentic 只是交换顺序，耗时 20.199 s，超过当前 18 秒读侧预算。
- **Agent 轨道的风险样本**：a1 把“新设备重建”case `6ac76ea7ad2d7bdce54730ce` 从第 2 位提到第 1 位，但前 3 位还出现了 bytedcli 和 KBase 相邻经验。a2 的 agentic case 最高分只有 0.06965，如果直接沿用现有 0.55 门槛，所有 case 都会被丢弃。这不证明它们都不相关，只证明不同方法需要独立校准门槛。

用户轨道平均耗时：hybrid 0.915 s、agentic 17.666 s。Agent 轨道平均耗时：hybrid 1.179 s、rerank 5.710 s、agentic 11.165 s。

## 局限与下一步

只有 4 个问题，每个组合只查一次，没有随机顺序、盲评标签或最终回答准确率评测；并发、缓存和线上负载也会影响耗时。以上只是当前空间的探索性证据，不能推广为稳定性能、成本估计或统计显著的准确率结论。

如果继续评估，先固定一组有目标记忆 ID 的历史问题，在包含去重、门槛和字数预算的真实注入链路中重复对比。分别观察目标记忆命中率、噪声、超时及最终回答质量，再决定是否开放按次升级；agentic 需独立门槛和回退预算。本次保留现有 hybrid 默认。

## top_k 对齐

- MCP 和核心都接受 `-1` 或 `1–100`，默认 5；禁止静默把调用值截到 20。
- 用户、Agent、v1 兼容请求都传同一个调用值，取消 Agent 固定 3 条。
- `-1` 是由服务端决定召回量，不能解释为无限量；读取 v1 返回值时不使用 `[:-1]`。
- 本次只读调用验证：v1 接受 `top_k=-1`（1.392 s，6 条 episode、10 条 case）；v2 也接受（1.729 s，33 条 episode）。问题均为“EverOS v1 v2 迁移”。返回数量仅代表该次查询。
- hook 默认仍传 5，v1 episode 最多 3 条、得分过滤、每轮 2000 字限制保持生效；MCP 格式化预算仍为 4000 字。因此扩大候选召回不等于把 100 条记忆全部塞进上下文。
