# EverOS 检索方法小样本对比（2026-10-09）

结论：保留 hybrid 默认；扩展评估发现 agentic 对隐含历史描述有可复现的补漏收益，适合作为补充检索候选。当前证据仍不支持默认开启 LLM rerank 或把每轮召回都改成 agentic。`top_k` 的本地 20 条上限没有记录依据，改为官方的 `-1` 或 `1–100`；默认仍为 5。

## 官方能力与当前选择

- `enable_llm_rerank` 只在 `agent_id` + `hybrid` 生效，增加 LLM 重排步骤；用户事件查询忽略它。因此开关不能改善全部记忆轨道。
- `agentic` 用更复杂的检索过程处理问题，不能与 hybrid 的得分直接比较；官方建议 hybrid 作为起点，复杂问题效果不足时再升级，并为 agentic 配更长超时及 hybrid 回退。
- `min_score` 只对用户 episode 的 hybrid 路径生效；切换方法不能假设现有 0.3 门槛仍有效。
- 桥接层原先把 `method` 写死为 hybrid，未开放参数，仓库没有基于本空间 A/B 证明 hybrid 总是更优的记录。当前 18 秒召回预算和 20 秒 hook 上限也不足以保证 agentic 完成。

来源：[Cloud 完整文档](https://docs.evermind.ai/llms-full.txt)、[官方 API 参考](https://github.com/EverMind-AI/EverOS/blob/main/docs/api.md#post-apiv2memorysearch)。Cloud 文档以本次成功的 HTTP 读取为准；其中的延迟/成本描述属于官方建议，不作为本机实测值。

## 试验口径

只调用现有空间的 `/api/v2/memory/search`，不写探针数据。固定 `top_k=5`；用户查询传 `min_score=0.3`、`include_profile=false`；Agent 查询仅在 rerank 组额外传 `enable_llm_rerank=true`。单请求超时 55 秒，最多 3 个并发。计时从请求发出至响应完成，不包含线程排队。未经过桥接层的去重、0.55 门槛或字数截断，以便观察原始差异。

| --- | --- | --- |

## 局限与下一步

只有 4 个问题，每个组合只查一次，没有随机顺序、盲评标签或最终回答准确率评测；并发、缓存和线上负载也会影响耗时。以上只是当前空间的探索性证据，不能推广为稳定性能、成本估计或统计显著的准确率结论。

如果继续评估，先固定一组有目标记忆 ID 的历史问题，在包含去重、门槛和字数预算的真实注入链路中重复对比。分别观察目标记忆命中率、噪声、超时及最终回答质量，再决定是否开放按次升级；agentic 需独立门槛和回退预算。本次保留现有 hybrid 默认。

## top_k 对齐

- MCP 和核心都接受 `-1` 或 `1–100`，默认 5；禁止静默把调用值截到 20。
- 用户、Agent、v1 兼容请求都传同一个调用值，取消 Agent 固定 3 条。
- `-1` 是由服务端决定召回量，不能解释为无限量；读取 v1 返回值时不使用 `[:-1]`。
- 本次只读调用验证：v1 接受 `top_k=-1`（1.392 s，6 条 episode、10 条 case）；v2 也接受（1.729 s，33 条 episode）。问题均为“EverOS v1 v2 迁移”。返回数量仅代表该次查询。
- hook 默认仍传 5，v1 episode 最多 3 条、得分过滤、每轮 2000 字限制保持生效；MCP 格式化预算仍为 4000 字。因此扩大候选召回不等于把 100 条记忆全部塞进上下文。

### 收益在哪里？

U01 两轮 hybrid 均未在前 5 条找到直接的 flush 时序根因记录，agentic 两轮都把它排在首位（11.800 s、16.695 s）。hybrid 返回的摘要主要是一般性修复、记忆导入和旧时间戳问题；agentic 的首条摘要直接包含“异步 add 尚未落地、立即 flush 返回 no_extraction、补 flush / async_mode=false”这些关键事实。这里确实存在可复现的补漏收益，不能仅因多等十余秒而排除。

用户轨道因此在每一轮都从 5/6 个问题命中目标变为 6/6；这一变化来自同一个问题，不是两个独立改善样本。其余 8 个问题，各方法均已首条命中目标，未观察到额外目标命中收益。三个 Agent 问题开启 rerank 的两轮也没有增加目标命中。

### 噪声和门槛有哪些限制？

查看代表样本发现：U03 的 agentic 前 3 条均围绕来源污染，hybrid 第 3 条为评测进度，相邻背景占位更多；但 U01 的 agentic 第 4 条又出现了 Libra 子实验记录。因此深检索也可能带入无关尾部，不能称为全面降低噪声。本轮没有完整盲评的相关性标签，不报告 Precision 或噪声率。

A02 的 agentic 首条是正确目标，第一轮得分只有 0.3827，直接套 0.55 会误删。方法间分数不可直接比较，若接入深检索必须单独处理门槛。目标记录被召回也不保证现有摘要包含所有回答事实；本轮没有测最终回答正确率。

### 如何决定默认方式？

本轮支持把 agentic 作为隐含描述、复杂历史问题的补充检索候选，并允许为可验证的质量收益适当延长等待；不因当前 18 秒预算否决它。尚不足以支持每条问题都默认改成 agentic，也没有支持默认开启 LLM rerank 的新证据。当前运行配置仍保留 hybrid。

样本从已知记录构造，容易使简单问题出现命中天花板，且只有 9 个独立问题、每组 2 次；上述 83.3%→100% 仅适用于本组用户事件问题，不能推广成通用准确率提升或统计显著结论。v1、画像、跨轮去重和全量真实注入未纳入本次方法隔离对比，实际整体收益可能不同。下一步若实施按次深检索，应验证方法专属门槛、字数预算和超时回退，再判断最终回答质量。

## MCP 按次深检索接入（0.3.3）

`memory_search` 增加 `method=hybrid|agentic`，默认仍为 hybrid；kind 和 top_k 语义不变。显式 agentic 使用45秒共同预算，默认先给33秒并为hybrid回退保留至多12秒。失败、超时或空结果按轨道回退，不覆盖成功的另一轨；输出展示回退提示，全部轨道技术失败则报错。v1始终hybrid，v1-only提示兼容降级。

agentic用户查询不发送min_score，做法结果不套hybrid的0.55；回退结果恢复对应门槛。格式化仍限制4000字，自动hook仍用原hybrid预算。功能回归由CI执行；真实MCP验证结果在PR中记录，检索研究结果不代替功能验收。

真实MCP验收：新进程初始化为0.3.3，schema公开method选项。用户事件agentic调用13.495秒返回直接flush根因；做法agentic调用10.937秒返回来源污染经验，目标得分0.3886仍保留。两次均无回退、isError=false，v1并行请求保持hybrid，输出1358/1730字。验证进程关闭全部记忆写入，仅调用只读search端点；[请求追溯及元数据](agentic-mcp-validation-2026-10-09.json)。失败、超时、空正文、门槛恢复和预算边界由CI离线回归覆盖。
